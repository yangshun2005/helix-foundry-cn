# 引导式设置

当工作区的设置尚未完成时，打开应用会直接进入 `/onboarding`；无需创建账户。设置流程依次经过 AI 选择、数据导入和建议本体（即本体步骤）。选择 Local、Claude 或 OpenAI 并按下 **继续** 会立即打开数据步骤；托管选项需要 API 密钥。保存选择和检查提供方在后台进行。确认本体会构建工作区并发布它；没有审核页面。服务器在发布事务的同时记录完成状态，随后设置会打开首页，首页显示从已发布数据中选取的关键指标。旧的仪表盘链接也会打开首页。

工作区存储可选的 `onboarding` 元数据。导入任务、加密的提供方准备任务、助手运行和提案使用现有的资源存储。无需迁移。保存并稍后完成会打开数据步骤，概览提供恢复设置。关闭浏览器不会取消工作。Worker 租约会恢复被中断的任务；上传内容在其任务被提交之前会被刷新到持久化存储。在任务待处理期间，请将传入目录以及数据集和 HelixDB 一并纳入备份。

## 数据与 AI

一个连接最多可以选择 100 张表或 S3 文件。每个选择会创建一个现有源和一个快照任务。只有明确选择的项目才会导入。数据库快照和 REST 分页必须完全完成，且在现有限制内（两百万条流式记录、1,000 个 REST 页面、每次上传 256 MB）。大型或失败的导入绝不会被示例数据替换。每次上传都会成为一个持久的异步任务；可以同时选择多个文件。失败的任务可以重试、取消、修正，或从设置选择中明确移除。移除输入不会删除它，也不会停止已在运行的导入。

本地 AI 会检查发布版本固定的模型，必要时拉取它，验证其摘要，并测试结构化输出。准备进度在重新加载后仍然保留。托管凭据在激活所选提供方之前会被加密并测试。如果替换失败，现有提供方设置保持激活；不会发生提供方回退。设置中的高级设置会暴露模型、端点和预算；引导过程会隐藏这些控件。引导过程中不会显示准备任务卡片。保存失败或提供方检查失败会显示重试和更改 AI 选择的选项，同时已导入的数据仍然可用。

**继续使用示例数据** 会高亮模拟的源一秒钟，并打开本体步骤，同时示例继续加载（`POST /demo` 带 `advance`）。本体步骤会显示正在到达的表，然后向 `/ontology` 请求建议本体：通过匹配键跨源合并的实体，以及它们之间的链接。它是根据数据确定性计算得出的；当 AI 就绪时，后台运行只会重写其摘要、描述和链接名称。**看起来没问题——构建我的工作区** 会确认它，支持可选的重命名和排除，并开始构建；已确认的实体和链接无需模型调用即可成为记录和关系，模型只设计仪表盘。该步骤随后以简单的阶段显示构建进度，并在发布时显示它已读取多少条记录和关系（运行的 `progress.records` 和 `progress.relationships`），在发布开始前可以停止（发布一旦开始就会完成，取消端点会以 409 拒绝），以及重试。没有人审核结果，因此经过两次修复后 SQL 仍然失败的组件会被排除，失败的操作以及任何验证失败的已确认流水线、类型或关系也会被排除。如果仪表盘修复调用本身失败，构建会保留可用的组件而不是失败。当没有组件保留时，仪表盘会被一个无需模型的计算概览替换：连接最多的实体的记录数、每个实体的记录数，以及当实体具有 created 或 date 列时每月的新记录数。经过验证的构建会以确认本体的用户（或最后重试它的用户）身份发布，运行以“工作区已发布”成功结束；如果它仍然验证失败或无法发布，运行会以原因失败，设置会提供重试，或返回建议。再次确认相同的选择会像重试一样重新启动失败或停止的构建，确认一个曾等待旧审核页面的构建也是如此。每次重试都会从保存的检查点继续，并使用全新的模型调用预算；每日 token 预算仍然适用。本体确认后，服务器仍会记录 `review` 步骤；UI 会将其显示为本体步骤的一部分。已确认的重命名和排除会作为 `ontologyEdits` 返回，因此再次查看建议时会从它们开始，关于被排除实体的注释会从构建中丢弃。当没有表具有标识其行的列时，建议没有实体，确认它只会构建仪表盘（其概览会统计每张表的行数）。在示例加载期间再次调用 `/demo` 会等待正在运行的加载，而不是再次加载它们。

推荐使用与构建相同的有界、掩码助手编排。它们的数据集/列证据会被检查，它们的模型使用会被计入，它们的结果会按输入签名缓存。设置只构建一个仪表盘，该仪表盘对 API 和 SDK 保持可用；应用不再显示仪表盘，而是使用首页的关键指标。所有 SQL、键和关系在发布前都会通过现有验证器。来自没有已确认本体的 `goal` 的构建（`POST /build`）仍会作为提案等待审核，并通过提案发布端点发布；对话式修订会产生一个新的经过测试的提案。

设置输入签名包括选定的源、不可变的数据集版本、待处理的 schema 更改和未完成的导入。更改目标会使选定的构建失效。发布会在提交内检查此签名、选定的运行、权限、提案哈希、输入版本和已发布代次。重新测试定义会保留其设置来源。摄取 API 到达的数据会被自动拾取，明确移除的输入除外。摄取会替换完整快照；它不是追加 API。

## API 与 SDK

所有路由都位于 `/api/v1/workspaces/:w/onboarding` 下，并且需要工作区访问权限。标记为（写入）的路由会拒绝只读 API 令牌：

| 方法   | 路由                  | 用途                                                                                                    |
| ------ | --------------------- | ------------------------------------------------------------------------------------------------------- |
| GET    | `/`                   | 服务器派生的进度、就绪状态、导入、推荐、构建和仪表盘                                                    |
| PATCH  | `/`                   | 保存步骤、延迟状态、目标和排除的输入 ID；没有可写的完成标志                                            |
| POST   | `/provider`           | 将所选提供方排队；可选的 `advanceToData` 会原子地保存数据步骤（写入）                                   |
| POST   | `/sources`            | 测试并导入明确的选择，带 `operationId`（写入）                                                          |
| PUT    | `/sources/:id`        | 修正现有连接并排队一次新的导入（写入）                                                                  |
| POST   | `/uploads`            | 暂存一个 multipart 文件；需要 `Idempotency-Key`（写入）                                                 |
| POST   | `/imports/:id/retry`  | 重试已停止的导入（写入）                                                                                |
| POST   | `/imports/:id/cancel` | 停止待处理的工作（写入）                                                                                |
| POST   | `/recommendations`    | 为完整的选定快照请求/缓存推荐（写入）                                                                   |
| POST   | `/build`              | 将 `goal` 构建为待审核的提案，可选地修订 `parentId`；在已确认本体的情况下，它会基于本体构建并发布（写入） |
| POST   | `/ontology`           | 计算（每个输入签名一次）并返回建议本体（写入）                                                          |
| POST   | `/ontology/confirm`   | 通过 `hash` 确认建议，带 `excluded` 和 `names`，然后构建并发布                                          |

现有的提供方、源、上传、摄取、助手、提案和发布端点保持兼容。SDK 新增了 `onboarding`、`updateOnboarding`、`prepareProvider`、`importSources`、`correctSource`、`uploadForSetup`、`recommendOutcomes`、`prepareOutcome`、`retryImport` 和 `cancelImport`。运行取消/恢复和提案发布使用现有的 SDK 方法。OpenAPI 可在 `/api/docs` 获取。

## 验证

`pnpm test:browser` 会在端口 3101、3102 和 5174 上启动隔离的 API、执行器和 Vite。它使用内存元数据存储、`.data/browser-isolated` 和一个确定性的本地提供方协议夹具，同时针对真实的 DuckDB 执行查询。它绝不使用实时 HelixDB、提供方凭据或演示归档。浏览器产物包括桌面和 390px 设置截图。该夹具仅在测试服务器中注册。

使用 Node 24 运行 `pnpm typecheck`、`pnpm test`、`pnpm build` 和 `pnpm test:browser`。连接器集成测试仍然单独选择加入；请为它们使用隔离的 MySQL/Helix 实例。
